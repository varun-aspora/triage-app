# 05. Decisions, rejected options, assumptions

Append-only. When a decision is reversed, add a new entry that supersedes it; do not edit history. Each decision names the option we did **not** take so the same debate is not repeated.

## Decisions

### D1. Runtime: Flue 2.x, with pi-ai as its provider layer
- **Chosen**: `@flue/runtime` for the agent loop, subagents, skills, HTTP routing, durability, `flue`-style CLI driving via `start()`/`init()`, Slack channel later.
- **Rejected**: (a) hand-rolled host on `@earendil-works/pi-agent-core`: would have to build HTTP, durability, subagents, skills and Slack ourselves; its one advantage, a native `beforeToolCall` argument-level gate, is replaced by D2. (b) pi coding-agent (`@earendil-works/pi-coding-agent`) with an extension: it is an interactive coding CLI, not a service; no HTTP, no Slack; not installed.
- **Why**: survey 07 comparison table. Everything the interfaces need already exists in Flue.
- **Consequence**: Flue is a Vite app and its evals are Vitest. The repo's Bun-only rule is amended (D18).

### D2. Gating lives inside tools and in what is mounted; no shell for the model
- **Chosen**: typed tools only. Each I/O tool calls a shared pure gate module before any network. Nothing generic (`bash`, `curl`, `psql`, file write) is mounted. No `useSandbox`. An `instrument()` interceptor denies unexpected tool names as a tripwire.
- **Rejected**: (a) porting the `PreToolUse` hook idea: there is no shell to hook. (b) Flue `useSandbox(local())` with a custom `SandboxToolFactory` for read-only file tools: `local()` "is not an isolation boundary" and the six built-in tools would have to be replaced anyway; simpler to write `repo_read`/`repo_grep` as plain tools with a path jail. (c) relying on pi-agent-core `beforeToolCall`: Flue does not surface it.
- **Why**: the current hook self-describes as an accident-stopper; the live allowlist drifted to 67 entries including `python3 *`. Gates owned by code are testable and do not drift.

### D3. Entity is a closure, not a parameter
- **Chosen**: one investigator subagent per enabled entity; its tools are constructed with the entity fixed. The orchestrator has no entity I/O tools.
- **Rejected**: a single investigator with an `entity` argument. It makes cross-entity leakage a one-token mistake and gives the model a wider surface for no benefit.
- **Consequence**: cross-entity reasoning happens only in the orchestrator, from summaries. Briefs must be complete because delegates do not inherit history.

### D4. One `.env` per deployment; names never encode the environment
- **Chosen**: `<ENTITY>_<SERVICE>_DB_URL`, `<ENTITY>_<SERVICE>_API_URL`, `<ENTITY>_QUICKWIT_*`, `SSFB_CBS_*`, `MODEL_*`, `TRIAGE_*`. `TRIAGE_ENV_LABEL` is display-only.
- **Rejected**: keeping `_DEBUG_`/`_STAGE_`/`_UAT_` infixes or `--env` flags. Also rejected: deriving structure purely by scanning env var names (fragile; a typo silently drops a service). Structure lives in `resources/<entity>.entity.json` (D5).
- **Why**: your brief; survey 03 §1 shows env and tenant were only lookup keys anyway.

### D5. Small per-entity registry file for structure
- **Chosen**: `resources/<entity>.entity.json` maps services to env var names, Quickwit `service` field values and repos. Loader fails at startup if a listed var is missing.
- **Rejected**: (a) generating it from `.env` (see D4); (b) hardcoding in TypeScript (harder for non-developers to review in a PR).

### D6. Allowlist: your `[{api, source}]` shape plus `methods`, `match`, `reason` — **superseded by D31**
- **Chosen**: `resources/<entity>.allow.api.json`, entries `{api, source, methods?=["POST"], match?="prefix", reason}`. `source` resolves to a base-URL env var, which is the host binding. `reason` is required.
- **Rejected**: the bare `{api, source}` form. The current file's own comment explains why: a path without a host binding lets the same path on another host through, and one existing entry uses an exact path on purpose so sibling mutating endpoints stay blocked. Dropping `methods`, `match` and `reason` would weaken the gate and lose review context.
- **Migration**: the four Shivalik entries move to `ssfb.allow.api.json`. ATSPL and RTL start empty.

### D7. SQL guard is a parser, not a regex
- **Chosen**: parse with a Postgres parser; accept one `SELECT`/`WITH…SELECT`; deny a function list; wrap `LIMIT`; server-side `$n` parameters; `default_transaction_read_only=on` and `statement_timeout` per connection.
- **Rejected**: porting `safe_sql.sh`'s keyword regex. It false-positives on identifiers (`last_update`), strips `--` inside literals, and its `-v` binding under `psql -c` is probably broken.
- **Still wanted, not ours to do**: read-only Postgres roles server-side (Q6).

### D8. HTTP: the model gives a path, never a URL
- **Chosen**: `http_get({service, path, query, customer_id})` builds the URL from the registry; `http_call_allowlisted` for the allowlisted non-GETs. `x-customer-id` set when known.
- **Rejected**: exposing a curl-like tool with option parsing (today's `safe_curl` spends 200 lines validating curl flags).

### D9. Classification is a code-driven step before dispatch, on a configurable model
- **Chosen**: `src/classify` calls `MODEL_CLASSIFIER` via pi-ai with structured output; a deterministic policy finalises the tier; the result is passed as `initialData`, and `Triage` picks its model from it.
- **Rejected**: (a) a separate Flue `Classifier` agent: doubles durable conversations per request for a one-second call. (b) letting the orchestrator classify itself: it would already be running on some model, defeating the purpose. (c) a `harness: true` tool inside Triage: the harness only exists inside an agent session, so the orchestrator's model would already be fixed.
- **Fail direction**: uncertainty routes **up** to the strong tier.

### D10. Escalation within a run is by delegation, not by switching models
- **Chosen**: `deep_investigator` subagent on `MODEL_TIER_STRONG`, always mounted; the method skill says when to use it.
- **Why**: Flue's `useModel` is submission-scoped; the model cannot change mid-run. Subagent `model` overrides can.
- **Rejected**: re-dispatching a new submission on a stronger model (loses tool-call history; doubles cost).

### D11. Code navigation: CodeGraph CLI via `execFile`, repo enum, plus jailed read/grep
- **Chosen**: `code_explore/node/callers/impact` wrap the CLI with `-p repos/<repo>`; `repo_read`/`repo_grep` under a realpath jail. Optional `codegraph sync` once per repo per run.
- **Rejected**: (a) Flue `useMcpConnection` to `codegraph serve --mcp`: Flue supports only `streamable-http`/`sse`, the server is stdio. (b) mounting the whole repos directory through a sandbox (D2). (c) running `git-clone.sh` in the request path: needs SSH to GitHub and ~50s.
- **Why**: survey 01 §5. CLI output for `explore`/`node` is identical to the MCP tools.

### D12. Claude Code / Codex integration is a skill that calls the CLI or HTTP, not an MCP server
- **Chosen**: a `SKILL.md` in this repo. Posting to Slack goes through `triage post <run_id>`, which asks for confirmation.
- **Rejected**: exposing the agent as an MCP server. Not documented for Flue; adds a second protocol to maintain for a benefit the CLI already gives. Revisit if a coding agent needs streaming.

### D13. Slack write is never an agent tool
- **Chosen**: ingress code paths only (`triage post`, `POST /triage/:id/post-to-slack`), always behind explicit approval. Reviewer handle and fallback group come from `.env`.
- **Rejected**: a `slack_post` tool with an "ask first" instruction. Prompt rules are not enforcement.

### D14. CBS direct read via bastion + kubectl stays, behind `SSFB_CBS_VIA_KUBECTL_ENABLED`
- **Chosen**: `cbs_read` mounted only when the flag is true; GET only; paths from the SSFB allow file (`source: finacle`); token passed on stdin and cached under `.data/cache`; k8s namespace, selector, container, secret and OAuth scope all from `.env`.
- **Rejected**: keeping `cbs_curl_via_eventbus.sh` as-is: token in argv on three hosts, writes the token into `.env`, heredoc quoting allows injection, denylist for extra args.
- **Closed 2026-09-23 (Q4)**: the OAuth mint is tool infrastructure, cache under `.data/cache`. Kube context and AWS profile are per entity (`<ENTITY>_KUBE_CONTEXT`, `<ENTITY>_AWS_PROFILE`, registry `kube` block); the login runs in pre-flight (D32), not in the tool.

### D15. The SSFB SSH tunnel is operator-managed — **superseded by D32 for local mode**
- **Chosen originally**: `triage doctor` reports tunnel status; `triage tunnel up` exists for laptops; the request path only checks reachability.
- **Now**: in `TRIAGE_DEPLOY_MODE=local`, pre-flight starts the tunnel before a real run (the process is owned by the CLI/server process, not a tool call). In `server` mode the original rule stands: infra owns it.
- **Still rejected**: starting `ssh -L` inside a tool call.

### D16. Knowledge is copied into this repo as Flue skills and fixed here
- **Chosen**: `knowledge/**` ported from triage-shivalik, contradictions resolved or marked unverified, Claude-Code wording removed.
- **Rejected**: reading the triage-shivalik CLAUDE.md tree at runtime by path. The files are mid-migration (root `CLAUDE.md` deleted, `.Codex` paths), contain 20+ contradictions, and reference wrappers that will not exist.
- **Cost**: two copies until triage-shivalik is retired. Accepted.

### D17. v1 scope is single-request, read-only triage
- **Deferred to v2**: batch/cohort status (DocketHub lists), Slack bot ingress, screenshot OCR beyond passing images to a multimodal model.
- **Refined 2026-09-23 (Q10, Q11)**: cohort is an ordinary SSFB service (DB, GET API, repo `cohort-service`) that any investigation may read; there is no separate batch mode. Incident impact analysis runs only when the request asks for it (classifier category `systemic`), not as a default step.
- **Never in scope**: executing remediation writes. They appear only under `suggested_fix` in the report (D35).

### D18. Toolchain: Bun for package management and scripts; Vite/Vitest where Flue requires them
- **Chosen**: `bun install`, `bun run`, `bun test` for the gate's unit tests; `vite build` for the Flue app; Vitest for `*.eval.ts` because Flue's eval harness is Vitest-based. Node ≥ 22.19 at runtime.
- **Rejected**: strict Bun-only (blocks Flue), or dropping Bun (no reason to). The rule file `.agents/rules/use-bun-instead-of-node-vite-npm-pnpm.md` is to be amended when implementation starts.

### D19. Mock mode is a first-class runtime flag
- **Chosen**: `TRIAGE_MOCK_MODE=true` routes every I/O tool to redacted fixtures; `TRIAGE_RECORD_FIXTURES=true` captures them. Evals and demos run with mock mode on. Your brief: never run real calls during implementation or evals.
- **Rejected**: mocking at the network layer (nock-style). Tool-level fixtures are simpler and match the audit granularity.

### D20. Audit log gains `run_id`, `interface`, `entity`, `decision`
- **Chosen**: schema in 02 §3. Refusals are logged. DSNs are never logged, only the env var name.
- **Why**: today's log cannot correlate a multi-entity run or tell a refusal from a failure.

### D21. Entity naming: `ssfb` is the canonical id for Shivalik
- **Chosen**: `ssfb` in file names and env prefixes, alias `shivalik` accepted in the registry. You used SSFB in the brief; the workspace uses shivalik.
- **Rejected**: keeping both as separate ids.

### D31. HTTP policy is one ordered rules file per entity: `resources/<entity>.api.rules.json` (supersedes D6 and the `never_call` list; refines D8)
- **Chosen** (your proposal, 2026-09-23): entries `{service, method, api, action: allow|block, reason?}`, evaluated top to bottom, first match wins; no match means GET/HEAD allowed and every other method blocked. `service` resolves to `<ENTITY>_<SERVICE>_API_URL` via the registry, which is the host binding. `:param` matches one segment, trailing `/*` matches a subtree at a segment boundary. Matching runs on the canonical built path. Loader rejects unknown services, unreachable rules, and over-broad allows. Semantics in 02 §4.4.
- **Consequences**: `http_get` and `http_call_allowlisted` merge into one `http_call` tool (method defaults to GET; the rules decide, not the tool name). `cbs_call` uses the same rules with `service: finacle`. The known mutating harbor triggers and the bro `PUT rules` become block rules instead of a separate registry list.
- **Rejected**: the two-file model (allowlist + never_call); `source` as the field name (`service` is the registry key, and it is what the model already uses in every other tool); making `reason` mandatory (the doctor warns instead, so the file stays as light as you asked).
- **Open**: whether read-only calculator POSTs (TD calculate, deposits config) may be allowed, since the current workspace rule says never re-issue them (Q25).

### D22. Identity resolution runs in ingress, before the classifier (supersedes the ordering implied in D9)
- **Chosen**: `identity.ts` resolves the ID chain and reads three basic state items deterministically; the classifier receives thread + IdChain + state. The same code is also the `resolve_identity` tool for mid-run re-resolution.
- **Rejected**: classifying on thread text alone. The survey shows Slack `Tag`/`Summary` misclassify often and re-routing happened after the first lookup. Fixing the model before any lookup would have baked that error in.
- **Source**: product-fit review.

### D23. `deep_investigator` replaced by `investigate_<entity>_deep`; escalation is deterministic; synthesis escalates through a harness tool (supersedes D10's mechanism)
- **Chosen**: per-entity deep delegates on `MODEL_TIER_STRONG` (same factory, entity still a closure). `note_evidence` sets `escalation.triggered` on low confidence, conflicting hypotheses, money movement on a non-strong run, or budget exhaustion. `finish_report` is a `harness: true` tool that, when triggered, re-synthesises the report on the strong model from the evidence folder.
- **Rejected**: an entity-less deep investigator (violates D3 and would hit Flue's duplicate tool-name error when mounting three entities' tools in one render); letting the cheap orchestrator decide whether it needs help.
- **Source**: product-fit and Flue reviews.

### D24. Redaction has two profiles and a stated residual risk (refines D2/D20)
- **Chosen**: model-facing profile keeps search keys (account numbers, UTRs, phones, UUIDs, names) and masks PAN, passport, card numbers, email local parts. Persisted/egress profile masks everything, decodes before scanning, uses names collected by ingress, and treats model free text as untrusted. `finish_report` refuses on a miss.
- **Rejected**: one profile applied to tool results. It would have hidden the account number the investigator needs to search logs with.
- **Residual risk accepted for v1**: free-text names or addresses that ingress never saw can pass. Recorded here so it is not rediscovered.
- **Source**: product-fit and security reviews.

### D25. HTTP surface is polling-only in v1; no `createAgentRouter` mount; HTTP Slack posting disabled by default (refines D13)
- **Chosen**: `GET /triage/:run_id` through egress redaction; `post-to-slack` behind `TRIAGE_HTTP_ALLOW_SLACK_POST=false` until the Slack bot can present a signature-verified approval. One shared bearer is a recorded v1 limit.
- **Rejected**: mounting Flue's agent router for SSE (streams model-facing data and exposes creation and arbitrary-conversation reads behind one token); trusting a caller-supplied `approved_by`.
- **Source**: security and Flue reviews.

### D26. Scope rule: id-shaped parameters must belong to the run's ID chain
- **Chosen**: `scope.ts` in the gate; `scope: 'systemic'` allows aggregate-only SQL and count/group-by log queries. Out-of-scope ids are audited as denies.
- **Rejected**: relying on the prompt to keep the model on the ticket's customer.
- **Source**: security review.

### D27. Fixtures are recorded to an unreviewed folder and promoted by a human; mock mode is the default
- **Chosen**: `TRIAGE_MOCK_MODE=true` by default; `TRIAGE_MOCK_STRICT=true` in evals; fixtures keyed by semantic key; recording goes to `fixtures/_unreviewed/` (gitignored) and is promoted only after a human reads it.
- **Rejected**: hash-of-input keys (miss on every run because model-written SQL varies); auto-committed fixtures (repeats the survey leak pattern).
- **Source**: product-fit and security reviews.

### D28. CLI gains `start`/`wait`/`status`/`ask`/`feedback`; `post` is non-interactive when stdin is not a TTY
- **Chosen**: coding agents call `triage start … --json`, poll `triage wait`, ask the human in chat, then `triage post <run_id> --yes --approved-by <user>`. `--thread-file` accepts a thread the coding agent fetched itself.
- **Rejected**: a blocking `run` as the only entry (coding agents' shell tools time out at 2–10 minutes); a y/N prompt as the only approval path (no TTY under Claude Code).
- **Source**: product-fit review.

### D29. Ports of `transfer_lifecycle.sh` and `list_transactions.sh` are SSFB tools; eval capture becomes `triage feedback`
- **Chosen**: `detect_silent_reversals`, `get_account_statement` on `investigate_ssfb`; `triage feedback` and `POST /triage/:run_id/feedback` write the existing eval front-matter.
- **Rejected**: expecting a mid-tier model to reproduce the DB-vs-statement join; dropping the only ground-truth pipeline.
- **Source**: product-fit review.

### D30. `cbs_call` carries data on stdin through a fixed remote script; the OAuth mint is tool infrastructure
- **Chosen**: charset-validated path; fixed ssh and kubectl argv; path, body and token as stdin data lines; no `sh -c`. The password-grant POST is performed by the tool to obtain a token and is not a model-reachable call; it is listed here as an explicit carve-out from "non-GET only via allowlist" pending Q4.
- **Rejected**: interpolating the path into a remote heredoc (the injection in today's script); treating the mint as an allowlist entry (it is not a model action).
- **Source**: security review.

### D32. `TRIAGE_DEPLOY_MODE=local|server` is the one env var code branches on, and only in pre-flight (Q3, Q4)
- **Chosen**: `local` means the process owns the network path: before a real run it brings the SSFB tunnel up, runs the per-entity kube/AWS login, probes hosts. `server` means infra owns the path: probe only. Failures never block; they become warnings for the caller and gaps in the report, and the affected tools answer "unreachable". Mock mode skips pre-flight. The variable is read in `preflight.ts` only; a test greps the rest of `src/` for it.
- **Why not a stage/prod flag**: deploy mode is orthogonal to environment. A stage `.env` on a laptop is `local`; a prod `.env` on a server is `server`. D4 still holds.
- **Rejected**: blocking the run when the tunnel fails (you asked for a warning; the run can still use Quickwit, other entities and code).

### D33. SQL runs inside `BEGIN READ ONLY` with `SET LOCAL` timeouts; role check warns by default (Q6, Q23)
- **Chosen**: one transaction per `sql_select` call: `BEGIN READ ONLY; SET LOCAL statement_timeout; SET LOCAL lock_timeout; <select>; COMMIT`. Postgres rejects writes and DDL inside a read-only transaction regardless of role, and `SET LOCAL` is permitted inside it. Works unchanged on a hot-standby reader node, where the session is read-only already. The parser refuses `SET`/`RESET`/`SHOW` so the model cannot lift the timeouts. The connection string also sets `default_transaction_read_only=on`.
- **Role check**: `has_table_privilege(..., 'INSERT')` true → doctor warning. `TRIAGE_REQUIRE_READONLY_DB_ROLE=true` turns it into a real-mode block per entity once infra provisions roles.
- **Rejected**: blocking by default (ATSPL and RTL would be unusable until roles exist); relying on the parser alone (client-side only).

### D34. Harbor field encryption is available to the SSFB investigator as two narrow tools (Q7; supersedes A6; widened to every service with a key by D48)
- **Chosen**: harbor uses AES-SIV, which is deterministic, so `encrypt_lookup_value` produces a ciphertext usable as a `$n` parameter for lookups by phone or CIF, and `decrypt_fields` decrypts values already fetched. Key in `.env` as `SSFB_HARBOR_FIELD_ENC_KEY`; the tools mount only when it is set. Plaintext follows the model-facing profile and is masked on persist. Audit lines record counts, never values. Native implementation (AES-SIV is standard RFC 5297), no `go run` dependency.
- **Rejected**: a generic "decrypt anything" tool; decrypting inside `sql_select` results automatically (the model should ask for it so the audit shows intent).

### D35. Remediation is rendered as `suggested_fix`, never executed (Q8)
- **Chosen**: the report carries cURL and SQL the human can run, with `$VAR` placeholders for tokens and hosts, preconditions and a verification query. The runtime has no code path that executes them. No `allow` rules for `trigger-delivery`, `sync-address`, `trigger-customer-creation`, `debit-unfreeze`, force-sign.
- **Rejected**: an "apply fix after approval" mode (out of the read-only scope; a v2 question at the earliest).

### D36. Tier policy raises to an image-capable model when the thread has screenshots (Q12)
- **Chosen**: pi-ai model metadata says whether a model accepts image input. If the selected tier's model does not and the request has attachments, the tier is raised to the first tier that does. `MODEL_TIER_STRONG` must accept images (doctor check). The classifier stays text-only when its model lacks vision and records `images_seen: false`; the tier model still gets the images.
- **Rejected**: a separate `MODEL_VISION` slot (another knob for the same thing); OCR pre-pass (v2 at the earliest, D17).

### D37. Repos are pinned by `resources/repos.json` (Q15)
- **Chosen**: `[{repo, entities[], branch}]`, `branch` defaulting to the repo's default branch. `triage repos sync` checks out, pulls and re-indexes outside the request path. The doctor warns on drift; the report records the commit per repo used.
- **Rejected**: tracking whatever is checked out (today's state, mostly `pre-prod`); pinning to deployed tags (no source of truth for "deployed" was named).

### D38. Persistence provider is configurable (Q20)
- **Chosen**: `TRIAGE_DB_PROVIDER=sqlite|postgres` + `TRIAGE_DB_URL`; `src/db.ts` selects the Flue adapter. sqlite is the laptop default.

### D39. Approval mode is configurable; `cli` in v1, `slack` buttons in v2 (Q22)
- **Chosen**: `TRIAGE_APPROVAL_MODE=cli` (interactive y/N or `--yes --approved-by`). `slack` will post the report with Yes / No / Comment buttons and treat the signed interaction as the approval proof. Until then `TRIAGE_HTTP_ALLOW_SLACK_POST` stays `false`.

### D40. All `api.rules.json` files ship empty (Q24, Q25; refines D31)
- **Chosen**: `[]` for every entity: GET and HEAD everywhere, nothing else. Every known mutating endpoint is POST or PUT, so no block rules are needed. The old allow file's bro and Finacle entries are not migrated; they come back by PR with a reason when a case needs them. The td-calculate example in the brief was illustrative.
- **Rejected**: seeding block rules for endpoints the default already denies (noise in the file; the loader would flag them as unreachable anyway).

### D41. Housekeeping answers recorded (Q9, Q13, Q14, Q16, Q17, Q18, Q19, Q21)
- Reviewer email and fallback group live in `.env`; a Slack bot token will be provided.
- Credential rotation after the survey incident is outside this project's scope by your decision; it is not raised again here.

### D42. Evals: promptfoo for model suites on top of Vitest contract tests; runtime skills; pseudonymised eval data (P1, 2026-09-23; refines D18, D20, D27, D29)
- **Chosen**: three layers. `bun test` for the gate. Vitest with pi-ai `fauxProvider` for scripted contract tests on every PR (in-process only, zero spend). promptfoo for case-file suites against real models: suite 1 (classifier + tier policy, no fixtures needed, side-by-side providers) and suite 2 (full Triage in strict mock over recorded fixtures). One shared `runCase()` driver. **v1 ships unit + contract + suite 1**; suite 2 waits for recorded fixtures, which do not exist yet.
- **Eval models are configurable per provider** (your decision): local Ollama, Anthropic, OpenAI direct, or another registered provider, set in the eval home's `.env` with the same `MODEL_*` keys plus `TRIAGE_EVAL_JUDGE_MODEL` (different family from the tiers under test; never OpenRouter under D41; a missing judge fails, it does not fall back) and `TRIAGE_EVAL_MAX_COST_USD`.
- **No real prod calls, in layers**: the eval home's `.env` has every entity credential blank; the driver refuses to start if one is set and forces `TRIAGE_MOCK_MODE=true`, `TRIAGE_MOCK_STRICT=true`, `TRIAGE_RECORD_FIXTURES=false`; every audit line carries `transport: real|mock` (D20 refined) and the `no_real_io` gate fails a case on any `real`. Config is selected by `TRIAGE_HOME`, never by a flag (D4).
- **One capture path, one promotion path** (D27, D29 refined): `triage feedback` writes the eval case draft to `evals/_unreviewed/<run_id>/`; `triage fixtures review` promotes fixtures and cases together. No separate evalset commands.
- **Pseudonyms, not masks, for eval data**: keyed, format-preserving pseudonyms so ids stay well-formed across thread text, ID chain, fixture semantic keys and the scope gate. Live runs keep the D24 masks.
- **Committing eval data**: reviewed cases and fixtures live in git, starting with the 4 verified cases; the 89 older thread conversions are promoted one at a time after a human reads each, because offline import cannot mask customer names the way ingress does.
- **Skills load at runtime** via `defineSkill()` over `knowledge/**/SKILL.md`, replacing static `SKILL.md` imports, so the agent boots under bun, Vitest and promptfoo alike.
- **Scope gate in evals**: hard fail only if an out-of-scope id was ever allowed; the model not attempting one is a soft metric.
- **Not added**: `root_cause.service` in the Report; service attribution is derived from `root_cause.code_refs[].repo` through the registry first, and the field is added only if that proves ambiguous.
- **Rejected**: promptfoo for everything (faux scripting needs in-process control); vitest-evals blueprint (its harness needs the agent router D25 keeps unmounted); a `--env .env.eval` flag (D4); a separate `point_in_time` metric (`taken_at` is already required by the schema).

### D43. Run store: provider interface, Postgres + pgvector in v1 on the Flue DSN, folder provider for sqlite deployments (P2, 2026-09-23; refines D20, D24, D38)
- **Chosen**: a `RunStore` interface owned by the app, separate from Flue's conversation persistence (Flue's own docs say business records do not belong there). The provider follows `TRIAGE_DB_PROVIDER` (D38): `postgres` → tables in a `triage` schema on the same `TRIAGE_DB_URL` (your decision: one DSN), with pgvector; `sqlite` → the folder provider at `.data/runs/<run_id>/` with brute-force cosine over `embeddings.json`, so laptops and evals behave the same. Tools reach the store through the same closure that carries `run_id`; the model never sees it. The idempotency key lives in the store. **One store per deployment**: a stage `.env` and a prod `.env` never share a schema or a runs dir, because the only column that could tell them apart is the display label, which code may not read (D4).
- **Model**: run → submissions (a `triage ask` follow-up is a new submission on the same run, so there can be several reports) → evidence, report, feedback. Audit stays in the JSONL (D20) as the single source; no audit table.
- **Text stored is the persisted-profile (redacted) text only.** The raw thread never enters the run store. Embeddings are computed over that text, never over the Flue stream. Two embedding kinds in v1: the case card (category, ask, root cause, status, pattern id) and the request. Exact cosine scan (`<=>`) with no index at this volume (about 150 cases a year); a per-model vector table so a model change is not a column migration. `triage runs reembed` rebuilds them.

- **Prior cases** go only to the orchestrator's initial data as a structured projection (ids stripped, no free text), never to the classifier: the classifier may run on OpenRouter, which D41 approved for this request's redacted thread only, and classifier confidence drives tier rules 1–3, so prior cases would change the tier through the back door. - **Rejected**: deferring Postgres to the server deployment (you chose to build it now); a separate run-store DSN; an HNSW index and a fixed `vector(n)` column; five embedding kinds; a `run_audit` table; prior cases in the classifier prompt; a `find_similar_cases` tool on the orchestrator in v1.

### D47. Repos sync on a schedule and before runs, at most `TRIAGE_REPOS_SYNC_INTERVAL` old (2026-09-24; refines D37)
- **Chosen**: `TRIAGE_REPOS_SYNC_INTERVAL` (default `24h`; `30m`, `2h`, `6h`, `1d` and so on) is the longest the checkouts may go without a sync. `TRIAGE_REPOS_SYNC_INTERFACES` (default `cli,http,claude-code,slack`; `none` turns it off) lists where it runs. With `http` listed, the server also runs a timer that checks every five minutes. Neither runs in mock mode, as pre-flight does not. `triage repos sync` and `POST /repos/sync` always sync; `triage repos sync --if-stale` is the cron or launchd entry for a laptop.

A sync where every repo failed waits 30 minutes before the next try, so a laptop off VPN does not retry on every run; a repo that keeps failing is named in each run's warnings instead of forcing a full sync every time. `<TRIAGE_REPOS_DIR>/.triage-sync.lock/` (with the pid) keeps the server, CLI runs and manual syncs from running at once; a lock whose process is gone, or older than two hours, is taken over. - **Rejected**: syncing on every run (every run would pay for about 21 fetches); syncing in the background while the run starts (files and the codegraph index would change under the code walker); a Flue schedule (Flue has no scheduler; the retention timer sets the pattern); keeping the record in the run store (it describes the checkouts, which live on disk next to it).

### D53. A run can pause on a question for the requester; CLI only in v1 (P6, 2026-09-25; refines D13, D25, D28; ends the "no questions mid-run" rule)
- **Chosen**: the Triage root gets `ask_requester`, for the one thing an investigator cannot look up: which customer when no id resolves, which of several matching records, the error text only a screenshot shows. It opens an input request in the run store and moves the run to the new phase `needs_input`; the model stops, the submission settles, and nothing runs while the person thinks (park, not hold). The record is presentation-neutral: question, why, fixed options, whether free text is allowed. The answer, or a skip, comes back through `answerRun` as a new submission on the same Flue conversation (a `triage.input_answer` signal), so the run keeps its history and evidence. Ids the person gives go through the ingress identity step and ride in the signal's attributes; the root merges them into the run's scope (D26). Free text never widens scope. The run's id chain is now mirrored into persistent state at every finish, so ids added mid-run survive the next submission and a new process; `triage ask` lost them before.
- **CLI**: `triage run` asks at the terminal and resumes in process, as often as the run asks; `triage wait` asks at a terminal too, or prints the question and exits 4; `triage status` shows it; `triage input <run_id> "<answer>" [--question q1] [--ids k=v] [--skip]` answers from another shell through the detached worker, like `triage ask`; `triage ask` refuses while a question is open. The Claude Code skill maps the question to AskUserQuestion and relays the user's own words.
- **Limits**: `TRIAGE_MAX_ASKS_PER_RUN` (default 2, raised to 10 on 2026-09-25; 0 leaves the tool unmounted), counted from the store so it survives a restart. The tool refuses a question that carries an unmasked identifier instead of masking it (a reader cannot answer "which of ****1234"), so the model rephrases with a date, an amount or the last four. Ingress names are masked in the stored question (D24). `finish_report` refuses while a question is open. Investigators do not get the tool; they return what blocks them and the root decides.
- **Not built (owner scoped this to the CLI)**: HTTP/web and Slack adapters. On `GET /triage/:run_id` a parked run shows `phase: needs_input` under `status: running` with no question, and `POST /triage/:run_id/ask` is not refused while one is open. `do` requests (a step on the host such as `qw login`) wait for the D32 answer. There is no deadline for an unanswered question: nothing runs while parked, so it costs nothing, and `triage input --skip` is the manual deadline. Ingress-time asks for a thread with no id are not built either.
- **Rejected**: holding inside a tool until answered (the store holds persisted text, so the tool would read an over-masked answer; the run timeout keeps counting; a crash settles the call as an unknown outcome); keeping the investigation going while waiting (same timeout, and delivery from a second process into the CLI worker is unverified); model-authored commands for a human (an injection surface, D2); a chat session in the CLI (a resident process is what breaks coding agents, D28, and there is nothing for it to hold); calling pi's `ctx.ui.*` or another framework's UI action (not in Flue's dependencies; the API shape was borrowed instead); a partial report as the carrier (it would flow into evals, embeddings and Slack posting); investigators asking directly (they render fresh per task and cannot use persistent state). Full reasoning in [proposals/P6](proposals/P6-mid-run-input.md).

### D54. A person can accept, reject or stop a run at any point; every step of a run is logged (2026-09-26; refines D29, D42, D43, D53)
- **Chosen**: a verdict no longer waits for the report. `triage feedback`, `POST /triage/:run_id/feedback` and the console's Accept / Reject buttons take a verdict at any phase, with optional notes and a verdict per finding. Accept is stored as `correct` and reject as `wrong`, so evals and the P4 learning work read one vocabulary. Each record keeps the run's phase, its latest submission and the submission whose report was judged, so learning can tell an early reject from a verdict on a finished report. The eval draft (D42) is still written only when the run has a report.
- **Findings get ids** without a schema change: `<entity>.v<version>.e<n>` (evidence item), `.h<n>` (hypothesis), `code.v<version>.c<n>` (code claim) and `root_cause`, derived from the stored findings versions (each `note_evidence` call stores a whole new version). A finding verdict keeps a copy of the finding's text, so learning needs no lookup later. `GET /triage/:run_id` lists the ids as `findings`.
- **Stop**: `triage stop`, `POST /triage/:run_id/stop` and the console's Cancel button. Cancel is a reject with no notes that also stops the run; the record carries `cancelled: true`, so learning can leave cancels out. The store marks the run `stopped` (a new terminal phase) in one step that also refuses a run that has already finished, and closes an open question as `cancelled`. Then Flue is asked for a durable abort of the instance. The process running the run reads the store every 2 s and aborts its own steps, and the store refuses phase writes on a stopped run, which catches a stop that lands between two reads. A follow-up (`triage ask`) resumes a stopped run.
- **Step log**: a Flue `observe()` subscriber, installed by `bootRuntime` in the worker and the server, writes every runtime event of a run to `<TRIAGE_RUNS_DIR>/<run_id>/events.jsonl`, next to `audit.jsonl`. The ingress pipeline adds its own lines (phases, pre-flight, identity, classifier, classification, dispatch, settle, failure with the full error, stop, feedback). Every line goes through the persisted redaction profile with the run's ingress names. `triage logs [--follow]`, `GET /triage/:run_id/events` and the console's Steps panel read it.
- **Left out of the log, because the same text is in another line**: streaming deltas, the conversation every `turn_request` repeats (the system prompt and tool list are written once per session and again when they change), `agent_end`'s message list and `turn_messages`' copies. Strings over 64,000 characters are cut, with the count cut.
- **Rejected**: new verdict values `accept`/`reject` in the store (two vocabularies for the same thing in evals); a stop that only records the verdict (the run keeps spending); SIGTERM to the worker pid (HTTP runs live in the server process, so the pid can be the server's own); a separate stop table or column (the Cancel verdict and the phase already say who stopped it and when); storing finding ids inside the findings (a schema change on every delegate for what the version and position already give); logging raw values for debugging (the stored-data rule of D24 and D43 has no exception for logs); writing every `turn_request` in full (a run's log grows with the square of its turns).

### D55. A run parks when a system it needs does not answer, and a person resumes it (2026-09-26; refines D23, D43, D53, D54)
- **Chosen**: a third way for a response to end, next to the question (D53) and the stop (D54). When a tool result says a system did not answer (`<entity>:<service> did not answer (unreachable | timeout | error)`) and the investigation cannot go on without it, the Triage root calls `stop_blocked` with the systems and one or two lines of reason. The store parks the run in phase `blocked` (not terminal; nothing runs) with the block record, the response ends with no report, nothing is embedded, and the Flue conversation keeps everything found so far. `triage resume <run_id> [message]`, `POST /triage/:run_id/resume` and the console's Resume button close the block as `resumed` and send the run on as a new submission of kind `resume` on the same conversation: a signal that names the systems, who resumed, and the person's message (what was fixed, and anything new the run should take into account, up to 4,000 characters), and tells the model to continue from what it has and end with `finish_report`, or `stop_blocked` again if a system still does not answer. Resume also works on a run that failed after dispatch and on a stopped run. A run that failed before dispatch has no conversation, so resume points at a new run.
- **Who decides**: the model calls the tool and the tool checks the claim. The tool pipeline records every `did not answer` outcome per run (system, tool, code, time), and `stop_blocked` refuses a system with no recorded failure, with the usual reply to record the gap and finish. A system the current ask does not need is a gap in the report, not a block; the instruction says so. Blank config (`not_configured`), gate refusals and fixture misses never count as a failure.
- **Why not the thin report**: with the finish check (one reminder, then failure) a dead database produced a completed run with an inconclusive report, embedded as a prior case and shown as done. A blocked run is not done: it is not embedded, it lists under its own status, and the console shows the reason and a Resume button instead of a report.
- **Store**: `block` (open) and `block_history` on the run, like the question; `putBlock` refuses while a question or another block is open and on a stopped run; `resolveBlock` closes it and leaves the phase to the caller; `markStopped` closes an open block as `cancelled`. Postgres migration 0003. A submission of kind `resume` carries `block_id` and `note`.
- **Statuses and exit codes**: CLI status `blocked`, `triage wait` and `triage run` exit 6; `triage ask` on a blocked run is refused and pointed at resume; HTTP list status `blocked`; console tone amber.
- **Owner alignment (2026-09-26)**: a stopped run with no submission is refused on resume like a failed one (no conversation to continue); resume closes an open block whenever one exists, not only in phase `blocked`, so a run that failed right after `stop_blocked` stored its record is not wedged; the resume carries a free-text message from the person, not only a note on what was fixed. Implementation deviations are in docs/10-implementation-notes.md (the CLI's takeover poll instead of a `dispatched` write, Cancel on a blocked run, the contract test recording the failure itself).
- **Left out**: a probe of the named systems before a resume (the signal says they are expected to answer; a resume into a still-dead system blocks again); a deadline for blocked runs (as for questions, D53); automatic resume when doctor sees the system back; Slack.
- **Rejected**: the system deciding alone from the audit (whether a failure blocks the case is a judgement, and the model has the context); the model deciding alone (it would bail on failures that do not matter; the recorded-failure check keeps it honest); reusing `stopped` for a block (a stop is a person's verdict and terminal; a block is the run's own state and expects a resume); reusing `triage ask` as the resume (the block record must be closed by the thing that resumes the run); storing the raw thread so a failure before dispatch could be replayed (D43 stands).

### D56. A lost database connection ends the call, not the process; a resume brings the SSFB tunnel back first (2026-09-26; refines D43, D55)
- **Chosen**: every client checked out of a pg pool carries an `error` listener for the life of the checkout, in the shared runner (`src/db/pg.ts`: Flue persistence and the run store) and in the SQL connector (`src/connectors/sql/pg-client.ts`). pg-pool listens on a client only while it is idle, and pg reports a socket that closes under a query both as a rejected query and as an `error` event on the client; with no listener Node ends the process. Now the query in flight rejects as before, the client is discarded on release, and the connector maps pg's "Connection terminated" to `unreachable` ("the connection to <env var> dropped"), a `did not answer` result the model can park the run on (D55). On the store side the transaction rejects and the run settles failed, which the resume for failed runs covers.
- **Why**: on 2026-09-26 a real run ended the process with `Unhandled 'error' event: Connection terminated unexpectedly` when a connection dropped under a query; the SSFB SSH forward is the likely peer (the local Docker Postgres logged nothing). A crash loses every run in the process and skips the blocked/resume flow built for this case. The rule stays: nothing waits or retries on its own; a run that hits an outage stops there and a person resumes it.
- **Resume**: `resumeRun` repeats the tunnel part of pre-flight (`runTunnelPreflight`, local mode only) before it writes anything, so `triage resume` and `POST /triage/:run_id/resume` bring the SSFB tunnel back when it died while the run was parked. A tunnel that does not come up refuses the resume (`ResumeNotReadyError`, a `RunNotResumableError`: exit 1 on the CLI, 409 over HTTP, the run left as it was, the warning and its fix in the message, a `resume_preflight` line in the run's event log). `triage resume` makes the same check in the foreground before it starts the worker, so the person sees the reason. Nothing else from pre-flight is repeated: logins and probes were made at the start, and a system that is still down blocks the run again on its own.
- **Rejected**: a process-wide `uncaughtException` handler (keeps a process alive with pool state nobody checked; the listener gives the same outcome through a defined failure); retry or reconnect inside a run (a bigger change, and it hides the outage from the person who has to fix it); probing the databases before a resume (the tunnel is the part that dies on its own; a dead database blocks the run again on the next call, and the block records it).

### D57. A lost database connection is tried again, bounded, with the SSFB tunnel brought back first (2026-09-26; refines D56)
- **Chosen**: both Postgres paths repeat a call that failed because the connection was lost or refused, up to `TRIAGE_DB_RETRY_ATTEMPTS` (the triage store and Flue persistence, default 100) or `TRIAGE_SQL_RETRY_ATTEMPTS` (entity databases, default 20). The wait starts at `TRIAGE_*_RETRY_DELAY_MS` (default 1 s), doubles each retry up to `TRIAGE_*_RETRY_MAX_DELAY_MS` (default 5 s), and carries jitter: a point in the upper half of that range, so waits neither collapse to zero nor line up across callers. At the defaults a store outage is ridden out for about eight minutes and an entity outage for about a minute and a half before the call gives up. Only connection-class failures qualify: network codes, SQLSTATE class 08, 57P01 to 57P03, 53300, and pg's own "Connection terminated". A query error, a server-side timeout, a refused login and an abort are never repeated. pg-pool opens a fresh connection for each attempt, so "reconnect" is the pool's; what the app adds is the repeat and, for SSFB in local mode, bringing the SSH forward back before each retry (`runTunnelPreflight`, the same step a resume runs), since the forward is the part of the path that dies on its own. Each retry is one `sql_retry` line in the run's event log (names and a code, never a message). The doctor runs with no retry, so a database that does not answer is reported at once.
- **What is repeated**: an entity call at any point, because it is a read-only transaction; on the store side a connect that failed, a read (SELECT or WITH) cut off at any point, and a transaction cut off before COMMIT was sent, whose function runs again on a fresh client. Not repeated: a single write cut off mid-statement and a COMMIT cut off, because they may have landed.
- **Why**: the owner's rule is that a database down for a while must not end the process (D56) and the run should carry on once it is back; on 2026-09-26 the owner set the store to 100 attempts and asked for exponential backoff with jitter capped at 5 s. A Postgres restart, a reader failover or a dropped forward now passes unseen; an outage longer than the window still ends in the D55 flow, a blocked run a person resumes, with the retries in the log. The entity default is lower because a tool call that waits is a run that waits, and a system that stays down has the block for it.
- **Rejected**: unbounded retries (a run that hangs on a dead system is worse than one parked with a reason, and the tool call has the run's budget and abort to respect); a fixed or purely exponential wait (jitter spreads retries from several runs and workers); repeating writes cut off mid-statement (duplicate rows or lost acks would be silent); retrying inside the HTTP and Quickwit connectors here (a different failure class; separate decision if wanted); a process-wide reconnect loop (the pool already reconnects per call).

### D68. The CLI ends the shared pg pools when its command is done (2026-09-26)
- **Chosen**: `main()` in `src/cli/main.ts` calls `closeSharedPgRunners()` (`src/db/pg.ts`) in a `finally` after `runCli`, whatever the exit code. It ends every shared pool and drops it from the map, so a later `getSharedPgRunner` in the same process builds a new one. The server entry is not touched.
- **Why**: with `TRIAGE_DB_PROVIDER=postgres` every command that opens the run store (`status`, `wait`, `ask`, `input`, `resume`, `stop`, `logs`, `runs *` and the rest) printed its output and then stayed alive until the pool's idle connections timed out (`idleTimeoutMillis`, 30 s). `triage status` now exits in well under a second.
- **Rejected**: `allowExitOnIdle: true` on the pool (it would change the long-running server and worker too, and a pool with an idle client still open is less clear than an explicit end); `process.exit()` in `bin/triage.mjs` (can cut off stdout that has not been flushed when output is piped); closing the store in each command (fifteen places to keep in step).
- **Assumptions**: no CLI command leaves work running on the pool after it returns; the worker awaits embedding and the usage flush before it settles.

### D69. Seven known ids, read from the thread by a decision model (2026-09-26; supersedes the id keys of D22)
- **Chosen**: a run knows seven ids: `country` (GB or AE), `phone_number`, `aspora_user_id`, `customer_id` (SSFB harbor customer_id, not the CIF id), `account_form_id`, `account_id` (SSFB rhythm account_id, a UUID, not the bank account number) and `account_number` (the bank account number). `resources/known-ids.json` describes each one: its description, the question asked about it, and either a candidate `pattern` with a `normalise` rule or, for `country`, the `options` with their aliases, plus the template `labels`. `src/config/known-ids.ts` loads and checks it; `KNOWN_ID_KEYS` in `src/types/core.ts` stays a literal list so the key type is a union, and the loader refuses a file whose keys differ from it or are out of order.
- **Extraction**: the identity step runs after the Slack thread is fetched (it already was). Code collects candidates from the raw thread with each value field's pattern, normalises and de-duplicates them. One `decide()` call asks a `choice` question per field, built only from the file: the field's question, one option per candidate of that field (option keys `c1`..`cN`, shown to the model in their model-facing masked form) plus `none`; `country` offers its options plus `none`. A value field with no candidates is not asked. The state is the same model-facing thread the classifier gets. A non-`none` answer maps back to the raw candidate, so every stored value is text from the thread, never text from the model. When one candidate is picked for two fields, the higher probability keeps it and the other field stays unset. `hints.ids` from the caller still win over both paths. The decision model is `MODEL_DECISION`, which replaces `MODEL_CLASSIFIER`: one model for every decision the pipeline makes, the classifier and the id extraction. A leftover `MODEL_CLASSIFIER` in the environment fails config loading with a message naming the new key. The id extraction uses it only when it is a decision spec (`typesafe/...` or `openrouter/...typesafe/...`). Its tokens and cost are counted with the run's intake usage (seq 0) as agent `identity`, purpose `identify`; `USAGE_PURPOSES` gained `identify` with no migration, since the pg column is plain text and the folder store checks rows with `UsageRowSchema`. Hinted keys are not asked, and hinted values are left out of the other fields' candidates. When the thread has no text, or every field was hinted, no decision runs and the event says `labels`. A gap is raised only when the decision path dropped candidates past the cap of 20 per field. `known-ids.json` is read from the home's `resources/`, falling back to the repo copy when the home has none (homes made before D69); an invalid file in the home is an error, not a fallback.
- **Fallback**: when `MODEL_DECISION` is unset or not a decision spec, or `decide()` fails, the step reads `<label>: <value>` lines using each field's `labels` (and the `country` aliases). Unlabelled UUIDs are no longer guessed into any key. The identity event says which path ran (`extractor: decision | labels`), the decision error when there was one (redacted), and each field's chosen probability; never a candidate value.
- **Hops**: `customer_id` to the harbor customer row; `aspora_user_id` to the harbor forms by `external_user_ref`; `account_form_id` to its form row, to the harbor customer by form, and to the SSFB then RTL `workflow_executions` by `reference_id`; `customer_id` to the rhythm accounts; `account_id` and `account_number` to the rhythm mapping and from there to `customer_id`, run before the customer hops when no customer id is known. `phone_number` and `country` have no hop and are passed to the agent as they are. The guardian device hop, the Horus and Alphadesk hops and the two-way `old_user_id` try are removed, as are `form_id` (the same id as `account_form_id`), `device_id` and `utr`.
- **Why**: run `01M3DEJYPHEV8WR9HGCAGFWEJE` sent `aspora user: <uuid>`. No label matched, so the UUID was placed under `old_user_id` as an unlabelled guess, a key whose name says nothing about what it is. The owner asked for the thread to be read by the decision model, for only these seven ids, and for the fields and choices to come from one JSON file rather than code.
- **Rejected**: a yes/no question per field followed by a regex for the value (the regex would still pick between two UUIDs); asking a chat model to write the ids out (values could be invented); keeping the old keys as aliases (two names for one id is how `old_user_id` came about); generating `KNOWN_ID_KEYS` from the JSON with `bun run gen` (a checked literal is simpler and fails the same way); a separate `MODEL_IDENTITY` key (the owner wants one decision model for every decision); keeping `MODEL_CLASSIFIER` as a silent alias (two names for one setting); trying `aspora_user_id` as a `customer_id` when it does not resolve (the key should mean what it says; the decision model tells the two apart).
- **Assumptions**: rhythm `customer_account_mappings` carries `customer_id`, `account_id` and `account_number` (the existing hop reads all three). Runs stored before this change keep their stored JSON; ids under the removed keys are dropped when those runs are parsed, with no migration. A phone number or account number is never sent to the decision provider unmasked: the model sees the same masked form the classifier sees.

### D70. A run's phase follows Flue's settlement, wherever it settles (2026-09-26)
- **Why**: run `01M3DEJYPHEV8WR9HGCAGFWEJE` stayed in `investigating` after its submission failed. Only the process that dispatched a submission and waits in `read()` wrote the final phase. Two server stops (most likely `node --watch` restarts) killed that process. Flue's lease recovery ran attempt 2 in a new process, then settled it failed (`submission_retry_exhausted`) in a third, where nobody was reading.
- **Chosen**: `src/ingress/settle-listener.ts` subscribes with `observe()` in `bootRuntime`, next to the event log and the usage meter, and maps a Flue event to a run the same way (`instanceId`, else `ctx.id`). On `submission_settled` it waits `SETTLE_GRACE_MS` (1 s, unref'd), reads the run and writes with the new compare-and-set `RunStore.setPhaseIf(runId, fromPhases, phase, detail)`:
  - failed or aborted: `failed` from `dispatched`/`investigating`, with the D67 reason built from the same `AgentRunError` that `read()` throws;
  - completed: `completed` from `investigating` only.
  `stopped`, `completed`, `failed`, `needs_input`, `blocked` and the intake phases are never overwritten. A settle is skipped when the run already has a later non-steer submission; the settled seq comes from the stored `flue_submission_id` (D71), else from the `dispatch` lines in `events.jsonl`. When it writes, it also marks the submission's usage rows final (summing a dead process's live flush with the recovery attempt's rows) and embeds the run the way the normal path does. Failures are logged as `settle_listener_failed` and never reach Flue.
- **Also**: `setPhaseIf` closes two older races. `investigating` is written after dispatch only from `dispatched`, so a fast tool's `needs_input` or `blocked` stays. The normal settle path writes its final phase from `dispatched`/`investigating` only, and writes nothing when the run is stopped, a later non-steer submission exists, or a later steer runs as its own response. Only the side that wrote the phase embeds, so each settle embeds once. Behaviour change: a failed read on a run parked on `needs_input` or `blocked` no longer overwrites that phase.
- **Rejected**: writing the phase on every settle (it would overwrite `needs_input`/`blocked`, and a late settle would clobber a newer submission); a second `adapter.connect()` to read Flue's submission rows; a long or non-unref'd timer (it would keep CLI processes alive, D68).

### D71. A running run nobody is working on shows as stalled (2026-09-26)
- **Chosen**: stalled is a display state. The phase and the API status stay `running`. Only `dispatched` and `investigating` can stall. `stalledOf` in `src/ingress/stalled.ts`, in this order:
  1. **no_owner**: the lease of the run's current Flue submission lost its owner more than `STALLED_LEASE_GRACE_MS` (60 s, two Flue scan rounds) ago. Owner lost is `leaseExpiresAt` for a running row and `settledAt` for a settled one.
  2. **no_owner**: the recorded CLI worker pid is dead. This counts only when there is no lease to read or the lease has also lost its owner. The pid belongs to the process that dispatched the head submission: every non-steer dispatch writes `worker_pid: deps.workerPid ?? null`, and `null` clears it (all three stores; no migration), so a follow-up from the server drops an old CLI worker's pid. Steers and settles write no pid. A failed `setSubmissionFlueId` is logged as `flue_id_write_failed`.
  3. **no_progress**: no line in the run's `events.jsonl` for `TRIAGE_STALLED_AFTER_MS` (default 600000, 10 min).
  `since` is when the signal started.
- **Which lease counts**: the head is the latest non-steer submission. A later steer with a Flue id is read first: a joined steer counts its host's lease, a steer running as its own response counts its own, a queued steer or one without a lease falls back to the head.
- **Storage**: each submission stores its Flue submission id (`triage.submissions.flue_submission_id`, migration `0002_submission_flue_id.sql`; the folder store and fake-pg match). It is set with `setSubmissionFlueId` after the dispatch receipt and checked by shape, not by the persisted profile, which would mask digit runs in the id. The lease is read through `src/db/submission-lease.ts`, which the wrapped `connect()` in `src/db.ts` fills; only `status`, `leaseExpiresAt`, `ownerId`, `joinedInto` and `settledAt` leave it, and every read returns null instead of throwing. `triage status` opens the leases itself without migrating. The last event time comes from the tail of `events.jsonl` (16 KiB, widened only for a longer line).
- **Where it shows**: `GET /triage/:run_id` and `GET /triage` (running rows of the page only, concurrently, with the internal ids stripped) return `stalled: {reason, since}`. `triage status` shows it in human and `--json` output. The web shows a `stalled` tag in the header and the runs list and a one-line reason.
- **Rejected**: recording `worker_pid` for HTTP runs (a `node --watch` restart gives a new pid while Flue is already recovering the run, so the run would look stalled); an in-memory last-seen map (empty after the restart we care about, and blind to CLI workers); the file's mtime; editing `0001_init.sql` (it is on main, and migrations are append-only).
- **Assumptions**: Flue's lease fields are marked lossy and unstable before 1.0, so they are used only as a live hint. Flue keeps `lease_expires_at` on settled rows and renews leases only while running (2.0.8).

### D72. Resume works on any run that is still going: a steer, or stop and resume (2026-09-26; extends D55)
- **Chosen**: `resumeRefusal` lets `dispatched` and `investigating` runs through once they have a submission. `needs_input` and `completed` keep their own actions (`triage input`, `triage ask`); `failed`, `stopped` and `blocked` resume as in D55. `resumeRun` reads the D71 signal:
  - **Not stalled, a steer**: a submission of kind `steer` with the note (persisted profile), dispatched to the run's instance as a user message, `renderSteer`: who, when and the note, model-facing redacted, with no instructions of its own. Flue joins it into the live response at the next turn boundary: after the tool calls of the turn in flight have finished and before the next model call (pi-agent-core `getSteeringMessages`). A tool call is never cut short or skipped. A contract test proves the order: tool result, then the note, then the next root model request. A steer needs a note. A joined steer writes no phase, usage or embedding; the host's settle owns them. A steer that misses the live response runs as its own response: the settle listener shows `investigating` on its `submission_running` and it settles like a follow-up.
  - **Stalled, stop and resume**: the stop is a compare-and-set from the phase the run was judged stalled in, to `stopped` with reason `stalled` and no verdict. Then Flue aborts the instance, the resume waits up to 30 s for the old submission to settle, and it continues through the D55 resume on the same instance and session. If the run moved on meanwhile, it is judged again from its new phase.
- **Answers**: `POST /triage/:run_id/resume` returns `mode: 'steer' | 'resume'`. A stalled resume answers 202 at once with `submission_id: null`; the stop, abort and resume carry on in the background, and the page shows "Resuming…" and keeps polling. One resume at a time per run, across processes: while a stalled stop is in flight (`stalledStopInFlight`: phase `stopped`, reason `stalled`, no submission newer than the stop's `updated_at`, and the stop under `STALLED_STOP_HOLD_MS`, 60 s, old), every caller gets `RESUME_HINTS.in_progress` (409 over HTTP). The resumer that did the stop goes on. A stop is left over, and can be resumed, once the resume added its submission and then died, or the hold has passed. A resume that fails after its stop and before its dispatch writes `failed` from `stopped` with the D67 reason (`recordStalledResumeFailed` over HTTP, the worker in the CLI). `triage resume` prints the mode and waits in the foreground.
- **CLI worker**: it never writes its pid or a phase for a working run before the stalled check; the pid goes with the resume's `dispatched` write, and a steer never writes one. A failed resume is marked failed only by compare-and-set over a phase the worker owns. A steer that throws leaves the run alone.
- **Report seq**: `finish_report` writes to the latest submission, so a joined steer's seq holds the response's report while the usage stays on the host's seq. The run's report is right either way. "Report vN of M" groups each steer with its host.
- **Rejected**: a signal message for the steer (it reads like a framework event, and Flue files it as a system message); appending into a tool call in flight; moving the report to the host seq (tools cannot tell which Flue submission they serve); aborting before the stop (the aborted settle could land first and mark the run failed); holding the 409 claim until the resumed submission settles (it would block steering it); a lock row in the store for the cross-process guard (a schema change that needs expiry anyway).
- **Assumptions**: process clocks agree to within a few seconds; `STALLED_STOP_HOLD_MS` assumes the 30 s abort wait.

### D82. Every run is traced to Braintrust when the home turns it on, redacted before anything leaves the process (2026-09-26)
- **Chosen**: `braintrust` 3.35.0, pinned exact, through `instrument(braintrustFlueInstrumentation())`, the path in Braintrust's docs. `src/tracing/braintrust.ts` is the only file that imports the package (source guard `braintrust-in-tracing-only`; test files may import it for the SDK's in-memory logger). It loads the SDK lazily, so a process with tracing off never runs its import side effects. Five keys in the `tracing` group: `TRIAGE_BRAINTRUST_ENABLED` (default `false`; a key alone does not turn it on, and enabled without a key is a config error), `BRAINTRUST_API_KEY` (secret; passed to `initLogger`, never copied into `process.env`, so `childEnv()` never hands it to a child), `BRAINTRUST_PROJECT_NAME` (default `triage-app`, per home), `TRIAGE_BRAINTRUST_CONTENT` (`metadata` default, or `redacted`) and `BRAINTRUST_APP_URL` (hybrid data plane only; not used today). Tracing never fails a run, a feedback command, a CLI command or shutdown: errors are swallowed and counted (`braintrustStatus()`).
- **Traces**: Flue 2.0.8 emits no `run_*` events for agents, so each submission's prompt operation is the root of its own trace. Model turns (`flue.turn`, type llm, with token metrics and cost) and tool calls (`tool:<name>`) are children of the operation, side by side; the bridge does not put a tool under the turn that asked for it. A delegation is a `task:<agent>` span under the operation with the delegate's turns and tools under it. The strong synthesis inside `finish_report` is a nested `harness.prompt()` with no parent the bridge can see, so it is a second trace with the same submission id. A tripwire denial of a delegation shows as a failed task span with the error class.
- **Redaction, two layers**: (1) the wrapped `observe` builds a new event from an allowlist (`src/tracing/redact-event.ts`) before the bridge sees it. Pairing and correlation fields (type, run, submission, operation, turn, task and tool call ids, session, model and provider fields, usage, timings) are copied as sent, so they never go through `redactPersisted` and the 6+ digit rule cannot break span pairing or ids. Content fields are replaced by their type and size in `metadata` mode, or go through `toPlain` and `redactPersisted` with the run's ingress names (`runRedactionNames`) in `redacted` mode. Error objects are projected too, because the SDK does not mask its `error` column: stacks are dropped in both modes, and `metadata` mode keeps only `type`, `name` and `code`. Image parts (`{ type: 'image', data }`, the D36 screenshots in the dispatch message and every turn's messages) are replaced by their type, MIME type and size in both modes, and so is any other base64 string of 1024+ characters that does not decode to text, because `redactPersisted` cannot mask a picture. Events the bridge does not read (deltas and the rest) are dropped. The wrapper stays synchronous, since Flue runs the matching interceptor right after `operation_start`, `turn_request` and `tool_start`. (2) `setMaskingFunction` runs `redactPersisted` without names on every field the SDK masks (input, output, expected, metadata, context, scores, metrics), then puts back id-shaped values of known id keys in metadata (`flue.*` ids, `model`, `provider`, `run_id`). The id shape allows `|`, for pi-ai's OpenAI Responses tool call ids (`<call_id>|<item_id>`). This layer drops image data too.
- **Model calls outside Flue**: `traceModelCall(kind, meta, fn, extract)` records `decision:<model>` and `embed:<model>` llm spans with `run_id`, token metrics and cost, under the same content mode. `decide()` traces every call that reaches the provider (classifier and identity), with the provider-reported cost; the classifier's completion path is traced too, priced with `priceUsage`. Ingress passes the run id to the classifier (`ClassifyInput.runId`) and to identity's `decide()` call. In `redacted` mode a span is masked with the names its caller passes (`ModelCallMeta.names`, `DecisionTrace.names`: the classifier's and identity's `redactionNames`) and the run's; the classifier's prompt keeps names for model-facing providers, so this matters. A call with neither a run id nor names is sent as type and size only. Embeddings are traced only when the caller passes `trace`: ingress sets `traced: true` for the prior-cases lookup and `embedAfterSettle` (which the settle listener uses too); `runs reembed` and doctor are not traced. The decision model runs before the Flue trace exists, so its span is a trace of its own tagged with the run id.
- **Feedback as scores**: a second instrumentation, installed after the bridge, captures each submission's root span (on Flue 2.0.8 the prompt's interceptor context has no submission id, so it is taken from the prompt's `operation_start`). `bootRuntime` writes the root's row id (`span.id`, what `logFeedback` takes) to `triage.submissions.trace_span_id` (migration `0003_submission_trace_span.sql`, no foreign key, checked by shape), found by the stored Flue submission id and retried at 250 ms, 1 s and 4 s when the root is captured before ingress has written that id. `submit.ts` also writes it, by seq, through `onTraceRoot` once the dispatch receipt is back, so a store write slowed by retries (D57) cannot leave it empty; a failed write there is a `trace_span_write_failed` pipeline line. Flue emits `submission_running` at the start of every attempt, and the capture forgets the earlier attempt's root on it, so a retry in the same process stores the new attempt's root. `recordFeedback` sends the verdict after the store write to the latest submission that has a span (`latestTraceSpanId`): `accepted` is 1 for correct, 0.5 for partial, 0 for wrong and none for pending, each finding is a `finding:<id>` score, and the notes go in the comment only in `redacted` mode and only when the run's ingress names are known, after `redactPersisted` with them; otherwise the scores go alone. It starts the logger itself, since `triage feedback` and `stop` never boot the runtime, and in such a process it waits (3 s at most) for the row to be sent. The SDK reports a failed send only through its background logger's `onFlushError`, which the install sets to count it. A failed or timed-out send there, or an error before the queue, writes a `feedback_trace_failed` pipeline line with the error class and never changes the feedback result. In the server the row goes with the next background flush, and a failed send is only counted.
- **Install and flush**: `bootRuntime` awaits `installBraintrust` after the usage meter and before `start()` (`braintrust: false` leaves it off). The tripwire is installed later, when `triageRuntime()` first builds the runtime, so Braintrust's interceptor is the outer one. `flushBraintrust()` waits at most 3 s, never throws, and returns how it ended (`off`, `done`, `failed`, `timeout`). The CLI calls it in `main()`'s `finally`, before the pg pools end (covers `run`, `feedback`, `stop` and the detached worker). When it times out, the SDK's requests and retry timers would keep the process up, so `bin/triage.mjs` drains stdout and stderr and calls `process.exit()`. The server calls it from the shim's `exit()` after `server.stop()`, because the aborted submissions' spans end during `stop()` and `process.exit()` skips the SDK's own `beforeExit` flush. `triage doctor` has a `tracing` row with the project name and content mode, from config only; the key and the app URL are named, never printed. Evals follow the eval home's env.
- **Rejected**: `bunx flue add tooling braintrust` (reads `process.env`, pins 3.17, observe-only and flatter traces); Braintrust's auto-instrumentation import hook (bypasses the redaction wrapper); OpenTelemetry to Braintrust's OTLP endpoint (a second integration for the same spans); turning tracing on when the key is present (too easy to enable by accident); masking only through `setMaskingFunction` (no run context, so no ingress names, and it runs after the span is built from raw content); redacting whole events and restoring ids afterwards (an allowlist copy never redacts them); reading the bridge's internal span maps for the root span id (internal state); `initLogger({ noExitFlush, onFlushError })` (initLogger does not hand them to the SDK's global state; `onFlushError` is set on the state's background logger instead); a separate `BraintrustState` (the bridge ignores it); parenting the decision span under the Flue trace (the trace does not exist yet); tracing in the classifier's and identity's `watched()` wrappers (would sit outside `decide()`'s time limit); a `getLatestTraceSpanId` store method (feedback already has the run loaded); checking the stored span id with the persisted profile (it masks digit runs in hex ids); flushing inside the sync `noteShutdown` (runs before `stop()` ends the aborted spans); having `recordFeedback` load config itself (a hidden env read in library code).
- **Assumptions**: feedback goes to the project of the process that sends it; only the row id is stored, not the project name. In `triage feedback` and `triage stop` the run's ingress names are not known (they are not stored), so a `redacted` comment is not sent from there; the scores are. A four-valued verdict maps to 1, 0.5, 0 and no score (owner to confirm). An eval home with tracing on runs under the no-I/O guard, so its Braintrust requests are blocked and counted, and no trace arrives. A failed model call's span has no token counts; the run meter still counts them.

## Mistakes recorded so they are not repeated

- **Regex redaction on `.env` values** missed quoted values and leaked DSNs into a transcript (survey incident). Redaction must be tested against quoted, exported and multi-line forms, and any tool that echoes config must whitelist key names rather than mask values.
- **IDE-maintained allowlists drift** (67 entries, `python3 *`). Gates belong in code under test.
- **Point-in-time reads reported as final** (eval case graded partial). Every state item carries `taken_at`.
- **Fan-out without a cap** took down a single-CPU Quickwit. Per-entity semaphores, default 1.
- **Token written into `.env`** by a script. Config files are read-only to the runtime.
- **`--env` defaults to prod with a warning** in two wrappers. There is no default environment in the new design; there is only the `.env` you loaded.
- **Interpolating a path into a remote shell** (today's CBS script). Remote hops take fixed argv and read data from stdin.
